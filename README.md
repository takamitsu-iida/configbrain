# configbrain

Cisco公式マニュアルを根拠として、要求に沿った有用なコンフィグ案を生成するプロジェクトです。
全要求を満たす根拠が揃わない場合も、根拠のある部分設定、未充足項目、確認できた制約を提示します。
推論候補は根拠付きコンフィグと分離し、適用可能な設定として扱いません。

## 開発方針

新しい開発指示と合格条件は[instruction.md](./instruction.md)を参照してください。
初期段階ではCisco Catalyst 9300 IOS XE 26.xの公式マニュアル群を対象に、
更新確認からPDF取得、OKF変換、検証、Qdrant登録までの取り込みパイプラインを構築します。
その後、要件から参照すべきマニュアルと章をLLMで選定する方式を評価し、根拠確認を経て
部分コンフィグを提示する処理へ進みます。

## 要件からコンフィグ案レポートを生成する

選定・検索・全文脈取得・コンフィグ案生成・Markdownレポート出力を一括実行できます。
対象はCatalyst 9300 / IOS XE 26.xです。**カタログ、検証済みOKF、原本PDF、
登録済みQdrant、ローカルの埋め込みモデルが必要**です。このコマンドは資料の取得や索引登録を行いません。
LLMの接続設定は後述の`CLOUD_GPT_API_URL`、`CLOUD_GPT_API_KEY`、任意の`LLM_MODEL`を共用します。

```sh
uv run python -m configbrain.pipeline \
  --requirement 'VLAN 120を作成し、アクセスポートに割り当てる' \
  --output-dir data/runs/vlan120
```

普段は出力先の`report.md`を開いてください。設定案と設定テンプレート、確認コマンド、
要件ごとの状態、不足情報、前提・注意事項、保留手順、分離した推論候補、各CLI行の出典を表示します。
PDFページ番号は章先頭であり、手順の掲載ページを検証したものではありません。
**評価用の案であり、実機投入や完成を保証するレポートではありません。**
処理中は段階名を標準エラーへ表示します。CPUでの検索やLLM応答には時間がかかります。

出力先には次のファイルを保存します。

- `selection.json`: LLMによる章選定
- `search-results.json`: 選定章内のQdrant検索結果
- `contexts.json`: 手順全体・注意事項候補
- `config-draft.json`: 検証を通過した評価用コンフィグ案
- `report.md`: 人向けのレポート
- `pipeline-state.json`: 実行条件、完了段階、各出力のSHA-256、失敗した段階と理由

途中で失敗しても完了段階のJSONは残します。同じ要件とオプションに`--resume`を追加すると、
出力のハッシュを照合し、最初の未完了段階から再開します。

```sh
uv run python -m configbrain.pipeline \
  --requirement 'VLAN 120を作成し、アクセスポートに割り当てる' \
  --output-dir data/runs/vlan120 \
  --resume
```

例えば生成で失敗した場合、選定・検索をやり直さず生成から再開します。
生成は既存CLIと同じ厳格な検証と、応答検証失敗時の1回だけの修正依頼を利用し、
パイプライン独自の追加再試行や検証緩和は行いません。
レポート出力だけの再開にはAPI認証情報は不要です。
保存済みの全文脈は現在のOKF・PDFから再検証します。
要件・カタログ・検索件数・資料の場所が変わった場合、出力が改変・欠落した場合、
または元資料との不一致がある場合は停止するため、新しい出力先で実行してください。
既存出力は`--resume`なしでは上書きしません。同じ出力先での同時実行は避けてください。

`--requirement-file requirements.txt`でUTF-8の要件ファイルも指定できます。
`--catalog`、`--database`、`--okf-root`、`--source-pdf-root`は各段階と同じ既定値を使い、
`--limit`（既定20）は要件項目×選定章ごとの検索件数です。

成功済みのコンフィグ案がある場合、LLMやQdrantを呼ばずにレポートだけ生成できます。
これは保存済みJSONの表示処理であり、元資料やコマンドの意味の再検証ではありません。

```sh
uv run python -m configbrain.report \
  --draft config-draft.json \
  --output report.md
```

**要件・カタログ目次は選定時に、要件・参照本文は生成時に設定先APIへ送信されます。**
機密情報を含む要件は送信しないでください。中間JSONとレポートには要件、
参照本文・引用、追跡用のローカル資料パスが含まれます。実機への設定投入は行いません。

## マニュアルカタログとPDF取得

Cisco公式のCatalyst 9300 / IOS XE 26.x掲載ページから、対象リリースの文書カタログを作成します。

```sh
uv run python scripts/discover_manuals.py \
  --product catalyst9300 \
  --release 26.x \
  --seed-url https://www.cisco.com/c/en/us/support/switches/catalyst-9300-series-switches/products-installation-and-configuration-guides-list.html \
  --output data/catalog/c9300-iosxe26.json
```

カタログには文書名、分類、PDF URL、対応するHTML目次URL、目次順の章タイトル・URL、
安定した文書IDが記録され、再実行時は掲載情報の新規・変更・削除を報告します。
HTML目次が見つからない場合や章リンクがない場合も状態を記録します。
PDF本文はHTTP `ETag`または`Last-Modified`で更新を確認し、同じ版でローカルの
SHA-256も一致する場合は再取得を省略します。更新時は`wget`で一時ファイルへ取得し、PDFとして検証して
から保存済み原本を置き換えます。サーバーから更新判定用ヘッダーが得られない場合は、安全のため再取得します。

```sh
uv run python -m configbrain.download_manuals \
  --catalog data/catalog/c9300-iosxe26.json
```

取得先は既定で`data/source_manuals/<document_id>/`です。別の場所を使う場合は`--destination`で指定できます。
原本PDFとローカル認証情報はGitへ追加しません。

## 取り込みパイプラインの実施順序

1. 公式掲載ページから文書カタログを作成し、前回との差分を確認します。
2. PDFの更新を確認し、必要な原本を取得・検証します。
3. 1冊をパイロット変換し、HTML本文、表、CLI、画像、PDFページ対応を検証します。
4. パイロット合格後、残りのPDFを個別にOKFへ変換します。各パッケージのFrictionless検証、
   章数・表・整形済みブロック・画像・ページ対応を確認し、問題のある文書は登録対象から外します。
5. 検証済みのOKFだけをQdrantへ登録し、文書・章・出典の情報を検索結果から追跡できるようにします。
6. 要件例を使い、ベクトル検索で候補を事前に絞らず、対象リリースの全マニュアルカタログから
   LLMが参照文書・章を選べるか評価します。複合要件は個別項目ごとに扱い、複数文書を選択できるようにします。
7. 選定した章の本文・表・手順を確認し、原本の出典位置と照合します。その後、根拠付きコンフィグ生成を評価します。

Qdrantへの登録は全対象文書の変換と検証が済んでから行い、失敗した変換を検索インデックスへ混在させません。

## 次段階: LLMによる参照マニュアル選定の評価

日本語要件をそのままベクトル検索する方式で検索漏れと誤った文脈の候補が見られたため、
次はマニュアル選定をLLMに委ねる方式を試します。ベクトル検索の上位結果で候補を絞らず、
対象製品・リリースの文書カタログ全体をLLMへ渡します。初期対象はカタログの全15文書・303章です。

- VLAN作成、アクセスポート、SVI、DHCPリレーなどの要件項目ごとに選定し、複合要件では必要な複数文書・章を返せるようにします。
- 出力はカタログに存在する文書ID・章URLに限定し、選定理由と判断の不確実さも記録します。
- 以前の13件の要件例、VLAN 120のパラメータシート例、Stateful DHCPv6の14手順を評価ケースとして再利用します。
- 正解文書・章のRecall@k、複合要件の項目網羅率、無関係な候補の割合を記録します。
- この段階では選定結果だけを評価し、コンフィグ生成や設定適用は行いません。Qdrantの結果は比較用の基準として残します。

探索的な1回の選定と評価は[評価結果](./data/evaluation/llm-manual-selection-20261118.md)を参照してください。
過去の結果を知った上での試行のため、独立した性能評価ではありません。
正解を固定した3回の別選定とQdrant比較は[固定正解の評価](./data/evaluation/selection-blind-20261118/report.md)に記録しています。

## LLMによる参照マニュアル選定

カタログの全章をクラウドLLMに渡して要件を項目に分解し、項目ごとの章候補を選びます。
Qdrantによる事前の候補絞り込みは行いません。`CLOUD_GPT_API_URL`と
`CLOUD_GPT_API_KEY`を環境変数またはローカルの`.env`に設定してください。
接続先はHTTPSのChat Completions互換APIで、認証には`api-key`ヘッダーを使います。
必要な場合は`LLM_MODEL`も指定できます。環境変数が`.env`より優先されます。

```sh
uv run python -m configbrain.select_manuals \
  --catalog data/catalog/c9300-iosxe26.json \
  --requirement 'VLAN 120を作成し、アクセスポートに割り当てる' \
  --output selection.json
```

`--requirement-file`でUTF-8の要件ファイルも指定できます。`--output`を省略すると
JSONを標準出力に表示します。`--output`に既存ファイルを指定すると成功時に置き換えます。
**要件とカタログ目次は設定された接続先へ送信されるため、
機密情報を含む要件を送信しないでください。** 出力にも要件が含まれます。

出力にはカタログのSHA-256、応答にモデル名があればその名前、要件項目、候補章の
文書ID・URL・選定理由・不確実性が含まれます。候補がない項目も残します。
不完全なカタログ、不正な候補、途中で切れたLLM応答はエラーとし、既存の出力を更新しません。
LLMによる要件分解の漏れや候補の妥当性は自動保証されません。
選定後の章本文とPDF原本の確認は別途必要であり、このコマンドは検索、コンフィグ生成、
設定適用を行いません。

READMEのVLAN例について、選定後の章内検索とPDF原本照合を試した結果は
[確認結果](./data/evaluation/vlan-evidence-pilot-20261118.md)を参照してください。

## 選定した章内の検索

選定結果JSONを入力し、要件項目ごとに選定された全候補章をローカルQdrantで検索します。
文書ID・章番号・章URL・製品・リリースで絞り込み、候補外の章へ検索範囲を広げません。
クラウドLLMへの接続は行いません。登録時と同じ埋め込みモデルがローカルに必要です。

```sh
uv run python -m configbrain.search_manuals \
  --selection selection.json \
  --catalog data/catalog/c9300-iosxe26.json \
  --limit 20 \
  --output search-results.json
```

DBは既定で`data/qdrant/db/`です。`--database`で変更できます。
`--limit`は**各要件項目の各候補章ごと**の最大件数で、既定は20です。
候補章の選定順を保持し、章ごとの類似度順に結果を返します。スコアの閾値は設けません。
`--output`省略時はJSONを標準出力に表示し、指定時は成功した場合だけファイルを置き換えます。

出力の`items[].chapters[].matches[]`には、点ID、順位、類似度スコア、本文、
文書・章・節、PDFと章HTMLのハッシュ、表行等の`source_refs`、章先頭のPDFページを含めます。
入力JSONとカタログのSHA-256、検索したコレクションと索引の識別子も記録します。
候補章がない項目は`no_candidates`、検索結果がある項目は`retrieved`、
候補章を検索して結果がない場合は`no_matches`として残します。
これらは根拠候補の取得状態であり、要件の充足判定ではありません。

選定時とカタログが異なる場合、不正な候補、索引に存在しない章、旧形式の出典情報は
エラーとし、既存出力を更新しません。DBを使用中の別プロセスがある場合も終了します。
**検索結果は原本照合前の候補です。** 上位チャンクだけでは手順や注意事項が欠ける可能性があり、
`pdf_page_index`も該当手順ではなく章先頭のページです。手順全体の取得、PDF原本照合、
コンフィグ生成・設定適用はこのコマンドに含みません。出力には入力要件と検索本文が含まれます。

## 手順全体と注意事項の取得

検索結果JSONの各ヒットを検証済みOKFの章・節へ対応付け、チャンクで分断された手順を
元のMarkdown/HTMLから取得します。LLM、埋め込みモデル、Qdrantへの接続は不要です。

```sh
uv run python -m configbrain.expand_context \
  --search-results search-results.json \
  --catalog data/catalog/c9300-iosxe26.json \
  --output contexts.json
```

取得範囲は次のルールで決めます。文字数での切り捨てや要約は行いません。

- `Procedure`、`Summary Steps`、`Detailed Steps`を直接の子見出しに持つ最寄りの節を
  手順の単位とし、その節全体を取得します。事前条件、手順の全Step、節内の注意書き、
  CLIブロック、後続確認を元の順序・表構造のまま保持します。
- そのような節がなければ、ヒットした節全体を取得します。
- 祖先の節にある導入本文と、同じ章内の前提条件・制約・ガイドライン・警告等の
  英語見出しを持つ節を追加します。別の手順に属する注意事項は追加しません。
  章全体の注意事項は広めの**確認候補**であり、要件への適用可否は未判定です。
- 同一章内の同じ範囲は重複させず、各ヒットの`context_ids`から参照します。
  異なる範囲が包含関係にある場合は重なることがあります。

出力の`items[].chapters[].contexts[]`に本文、取得理由の`roles`、章本文内と
元のOKF本文内の1始まり行範囲（両端を含む）を記録します。
章にはOKF本文・PDFのパスとハッシュを保持します。本文中の相対リンク・画像パスは
元のOKF本文を基準とします。入力検索JSONのハッシュも記録します。

取得前に全OKFのFrictionless検証とPDF等のハッシュを再確認し、カタログ・索引世代・
検索ヒットの出典情報を現在の資料と照合します。資料が変わった場合や、節の位置が
一意に決まらない場合はエラーとし、既存出力を更新しません。
`--okf-root`と`--source-pdf-root`で資料の保存場所を変更でき、`--output`省略時は標準出力に表示します。

**原本PDFの内容照合は未実施です。** PDFハッシュの一致は本文内容の確認を意味しません。
章外への参照リンクを自動ではたどらず、見出し規則だけで注意事項の網羅性・関連性も保証しません。
`evidence_status`は引き続き`candidates_only`、`pdf_verification_status`は`not_verified`です。
PDFページは章先頭の位置のままであり、コンフィグ生成や機器への適用も行いません。

## 評価用コンフィグ案の生成

取得した根拠候補からクラウドLLMで案を生成します。選定CLIと同じ
`CLOUD_GPT_API_URL`、`CLOUD_GPT_API_KEY`、任意の`LLM_MODEL`を使います。
未作成の場合は先に`expand_context`で根拠JSONを作成してください。

```sh
uv run python -m configbrain.generate_config \
  --contexts contexts.json \
  --search-results search-results.json \
  --catalog data/catalog/c9300-iosxe26.json \
  --output config-draft.json
```

**要件と取得済みのマニュアル本文を設定先APIに送信します。機密情報を含む要件を
送信しないでください。** 本文はHTML装飾を除いて送信し、ローカルの資料パスは送信しません。
出力には要件・本文と、追跡用のローカルパスが含まれます。

送信前に元の検索JSONから根拠を再取得し、`--contexts`と一致することを確認します。
このため元の検索JSON、カタログ、検証済みOKF、原本PDFも必要です。
変更された根拠や古い資料を使った案は生成しません。
生成は要件項目ごとにAPIを呼び出し、その項目で使用できる出典と構文IDだけを渡します。
同じ構文を持つ別手順のIDや、別の要件項目の出典を取り違えないための分離です。
応答の検証に失敗した場合だけ、同じ出典・元の応答・検証エラーをAPIへ返し、
1回だけ修正を依頼します（1項目あたり最大2回のAPI呼び出し）。
修正後も同じ検証を適用し、不正なら停止します。成功時の修正履歴は`validation_repairs`に残します。
各応答を検証し、全項目が成功した場合のみ出力します。失敗時は要件項目、
コマンドの検証エラーには配列内の位置も表示します。
変数の不一致・値の形式不正には構文IDと変数名も表示します。
`--search-results`の既定は`search-results.json`で、
`--okf-root`と`--source-pdf-root`も前段と同様に指定できます。
`--output`省略時はJSONを標準出力に表示します。

出力の要件項目は省略せず、`supported`、`partial`、`not_found`、`conflict`、
`needs_input`の状態と判断理由を残します。`configuration`は根拠に沿う部分設定、
`verification`は確認コマンドです。未指定パラメータを含むコマンドは
`templates`／`verification_templates`に分離し、項目を`needs_input`にします。
不足情報、前提、出典付きの制約、採用を保留した手順、分離した推論候補も記録します。
出典の手順行に`(Optional)`と明記されたコマンドを省略しただけでは未充足としません。
保留手順の`optional`はモデルの申告ではなく出典から決定し、必須手順の保留・不足情報・仮定が
残る項目を`supported`として扱うことは引き続き拒否します。

各CLI行は手順表の`Command`／`Command or Action`列から抽出した構文IDを参照します。
一つの変数タグ・斜体タグに複数の変数（例: `ip-address subnet-mask`）が
含まれる場合も、変数を分けて抽出・置換検証します。
構文の選択肢・省略可能部分とパラメータ置換を検証し、値は入力要件に含まれる文字列か、
テンプレート用の明示的なプレースホルダーに限定します。任意のCLI追加や、資料の例示値を
要件値とみなす補完は認めません。表外のコード例は参考本文として送信しますが、
この版では根拠付きCLIの抽出対象にしません。
IPv4 CIDRを明示した要件では、プログラムで計算したアドレス・サブネットマスクを
`normalized_ipv4_networks`としてLLMにも渡します。`subnet-mask`／`subnet_mask`に限り、
同じCIDRのアドレスと組み合わせたマスク表記への変換を許可し、bindingの`derivation`に記録します。
例えば`192.0.2.1/24`に対する`255.255.255.0`は推測値ではなく計算で照合します。
IOSのインターフェース識別子に限り、大文字小文字だけが異なるLLM応答は要件中の表記に戻し、
`normalizations`に記録します。略称の展開や別ポートへの置換、VLAN名などの大文字小文字の同一視は行いません。
`bindings`の各値は`{"value": "120", "origin": "requirement"}`のようなオブジェクトが必要です。
`{"vlan-id": "120"}`という省略形式は受け付けず、LLMへの修正依頼の対象になります。
LLMがパラメータ値をJSON整数（例: `120`）で返した場合は文字列へ正規化してから同じ検証を行います。
未指定値（`null`）、真偽値、小数値は補完せずエラーにします。
未使用の選択肢に空文字列が返った場合は、その値なしでもCLIが出典構文に一致することを確認し、
`omitted_bindings`に記録して除外します。必須の値が空ならエラーにし、値を推測しません。
テンプレートにはプレースホルダー行だけでなく、その手順の固定コマンドも同じ配列に順序付きで保持します。
`templates`／`verification_templates`もコマンド行のフラットな配列であり、
`{"commands": [...]}`では囲みません。プレースホルダーは`<INTERFACE_ID>`のように
英大文字で始まり、英大文字・数字・アンダースコアだけを含む形式です。

各行の`citations`から`sources`の文書・製品・リリース・章・節・OKF行範囲・
PDFハッシュへ追跡できます。`table_index_in_context`は取得範囲内の表番号であり、
Qdrantの章全体の`table_index`とは異なります。説明や制約の引用も出典本文との一致を検証します。
モデル名が返れば項目ごとに`item_models`へ保存し、全項目で同じ場合は`model`にも保存します。
入力のハッシュと索引世代も保存します。

**出典・構文の一致は、意味的な妥当性、モード遷移、コマンド順序、パラメータの許容範囲、
必要な手順の網羅性を保証しません。** 要件との対応や充足状態はLLMの判断であり、
資料に存在する値でも適切とは限らないため、人による確認が必要です。
`evidence_status`は`candidates_only`、`pdf_verification_status`は`not_verified`、
`ready_to_apply`と`configuration_complete`は常に`false`です。
原本照合や機器への投入は行いません。

1回の修正後も残る不正な出典・構文・応答や要件項目の脱落は明示的に失敗とし、
既存出力を更新しません。途中で切れた応答・APIエラーは修正依頼や自動再試行をせず失敗します。
プログラムによる一般知識・推測での補完や、検証の省略は行いません。

## OKF変換パイロット

まずIP Addressing Services Configuration Guide 1冊で、カタログに記録された章HTMLを
Markdown化します。表は行・セル構造を保つためHTMLのまま埋め込み、CLI等の整形済みブロックは
表内のものも含めHTMLのまま保持し、表外のものはコードブロックとして保持します。
PDFページは、PDF本文の`CHAPTER`見出し直後に章名が一意に
一致した場合だけ割り当て、それ以外は未対応として記録します。

```sh
uv run python -m configbrain.convert_manual \
  --catalog data/catalog/c9300-iosxe26.json \
  --document-id catalyst9300-26-x-b-26x-ip-9300-cg-a541d83b236d
```

出力先は`data/okf/<document_id>/`です。`manual.md`、PDFと各HTML章の出典・ハッシュ・
ページ対応を記録した`provenance.json`、HTML画像リソース、およびFrictionlessで検証した
`datapackage.json`を生成します。これは品質評価用の1冊の試験変換です。パイロットの検証後に
残りの文書へ適用します。生成データは原本同様Gitに追加しません。
取得できない画像は元URLを残し、未取得状態を`provenance.json`と実行結果に明示します。

## Qdrantへの登録

検証済みの全OKFパッケージを、Qdrantの永続ローカルモードで登録します。
Qdrantサーバーは不要で、DBは`data/qdrant/db/`、検索用の別名は
`c9300_iosxe26_manuals`です。日本語の要件から英語のマニュアルを検索できるよう、
埋め込みはCPU上の`intfloat/multilingual-e5-small`で生成します。
登録するテキストには`passage:`、検索クエリには`query:`の接頭辞を付けます。

```sh
uv run python -m configbrain.index_manuals \
  --catalog data/catalog/c9300-iosxe26.json
```

登録前に各OKFのFrictionless検証、原本PDFと画像のハッシュ、章とPDFページの対応を確認します。
表は列見出しとセルの対応を含む行単位、CLIブロックと本文は出典メタデータ付きチャンクとして
登録します。表内に空行や入れ子の表がある場合も表全体を解析し、各行の`source_refs`に
表番号・行番号と、章本文内での表全体の行範囲を記録します。行範囲は個別の表行の位置ではありません。
`pdf_page_index`は1始まりのPDF物理ページ番号ですが、個々のチャンクのページではなく
章先頭の位置です。`pdf_page_scope`は対応済みなら`chapter_start`、未対応なら`unmapped`であり、
根拠箇所のページは別途原本で確認する必要があります。
索引形式の変更時も再登録します。新しいコレクションの点数とIDを検証してから別名を切り替えるため、登録失敗時は
既存の検索対象を維持し、同じ入力で再実行しても重複しません。QdrantのDBはローカルデータのため
Gitに追加しません。
