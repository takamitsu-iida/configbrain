# configbrain 進捗管理

更新日: 2026-11-20

現在地、次の着手点、残課題、評価履歴を管理する。
現行仕様は[基本設計](./basic-design.md)・[詳細設計](./detailed-design.md)、
実行・開発手順は[実装ガイド](./implementation-guide.md)を正とする。
将来案・未評価事項を実装済み仕様に混ぜない。

## 1. 現在地と次の着手点

### 現在地

- ガイド・リファレンスの取り込み、混在資料の検証、選定からレポートまでの接続は実装済み。
- 起動・再開時は両資料と同一世代の索引を必須とする。ガイドだけの旧DBから移行済み。
- 引用のHTML／PDF照合と、説明の主張・適用条件の意味審査は実装済み。
- ただしdemo24では意味審査の応答検証が全件失敗し、有用な審査の完了性・精度は未達。
- 資料選定は現在も章タイトル中心。節・手順の意味付きメタデータは未実装。

### 今回の文書整理

- READMEを利用者向けのセットアップ・生成・結果の読み方・再開に整理した。
- 旧`instruction.md`の開発指示とREADMEの保守用CLI説明を実装ガイドへ統合した。
- 基本設計から実行結果・改善バックログを本書へ移した。
- 旧コマンドリファレンス設計は[過去の統合記録](./history/command-reference-integration.md)へ移し、
  当時の中断・再開メモを現行の着手点と分離した。
- 評価用Markdownは[評価資料](./evaluation/)へ移動した。
  JSON・採点プログラム・原本・DB・runは元の場所に残した。
- この整理では実装・資料・索引・過去runを変更せず、追加のLLM評価も行っていない。
- 検証: Markdown 10文書のローカルリンク・アンカー96件、16コマンド例のオプションを
  11個のCLIヘルプと照合した。固定評価手順とdemo24の主要5成果物のハッシュ不変を確認した。
  文書のみの変更のためpytestは再実行していない。

### 次に行う改善: 資料選定メタデータ

利用者の方針として、文書整理の後はこの改善から着手する。
以下は合意した方向であり、スキーマ・分割方法・合格閾値の詳細は未確定。

1. 公式本文から章・節・手順の構造と所在をプログラムで抽出する。
2. 節・手順を基礎に、LLMで「扱う操作・答えられる質問・短い説明」を生成する。
3. 生成説明を本文範囲に結び付け、章ごとの選定用情報へ集約する。
4. メタデータは候補発見専用とし、CLI・適用条件の根拠は従来どおり原文に求める。
5. 本文更新時の再生成条件と、未生成・生成失敗時の扱いを決める。
6. 同じ要件・正解集合で現行方式と比較し、必要章の選択漏れ・不要候補・入出力量を測定する。

着手時に[詳細設計の選定契約](./detailed-design.md#52-選定)を確認し、
取得・メタデータ生成と、利用時の選定を分離して設計する。
文書全体の一括要約だけで、細かな手順の所在を失わないこと。
本文範囲の存在検証だけで要約の意味的正しさまで証明できたとは扱わない。
既存のCLI根拠制限、項目境界、原本照合を緩める変更は含めない。

## 3. 改善バックログ

I-01〜I-09は設計整理時の優先度案。直近は利用者が選択したI-05のメタデータ改善に着手する。
他の課題が解消したわけではなく、意味審査の完了性・精度は引き続き重要な未解決事項である。

| ID | 優先度案 | 改善対象・現状の制約 | 方針の候補 | 判断に使う受け入れ条件 |
| --- | --- | --- | --- | --- |
| I-01 | 高 | 意味審査が長い応答の全件成功を要求し、demo24では修正段階へ到達しない | 文脈を保持した対象分割、短いローカル根拠ID、応答単位のチェックポイント | 全単位の最終被覆、審査完了率・修正到達率・時間・入出力量を測定し、欠落や不正IDを承認しない |
| I-02 | 高 | 同じLLMによる審査の意味的な精度が未確立 | 人手ラベルの正例・負例を独立した評価入力として固定し、実モデルを測定 | 出典の不当支持、適用性の不当確定、過剰保留を別々に評価。単なるスキーマ合格を正解としない |
| I-03 | 高 | 説明・項目間依存・実機前提に不整合が残る | 事実、計画上の順序、機器状態、資料上の必須条件を分離して表現 | VLAN groupとaccessの混同、VTP条件の除外、任意の順序を必須依存とする説明が残らない |
| I-04 | 中 | PDF抽出順や改行等で原文がある引用も未一致、短い共通文は複数一致 | 表セル対応・断片位置・章内近傍による照合を評価 | 原本で人手確認した評価データで一致率向上と誤一致ゼロを両立。比較条件の一律緩和はしない |
| I-05 | 中・次の対象 | 選定漏れ・節外参照・明示リスト以外の子コマンドは自動追跡が限定的 | まず節・手順の所在とLLMによる意味付きメタデータを導入。参照追跡・解析拡張は別に扱う | 必要章・手順・反証の再現率と誤採用率を測定し、不明な親・モードは未確定のまま扱う |
| I-06 | 中 | 長い引用・繰り返す検証失敗が本文を膨らませる | 結論、未確認事項、根拠断片、完全な診断履歴を表示上分離 | 利用者が採用可否と次の確認を短く把握でき、完全な出典追跡も失わない |
| I-07 | 中 | HTML由来OKFとPDFの対応、および資料一式の切替は全体トランザクションでない | 原本の定義・照合範囲を明文化し、候補資料一式を検証して切替 | HTMLとPDFの版違いを検出し、更新失敗時も直前の正常な資料・索引を使える |
| I-08 | 中 | 再開は大きな段階単位で、モデル・プロンプト等の実行仕様を完全には固定しない | 機能版管理・入力スナップショット・内部再開粒度を検討 | 旧結果の再利用条件が明確で、仕様変更時に古い承認を誤用しない |
| I-09 | 低 | 生成・検証・表示の大きなモジュールに責務が集中 | 安定した契約を決めた後、根拠・状態・API制御などの境界で分割 | 同じ保存入力のCLI・判定・レポートを保ち、単独で検証可能な境界ができる |

デフォルト設定の自動省略は未実装で、メタデータ改善の対象に含めない。
将来導入する場合は、直接的なデフォルト根拠、製品・モード・適用条件、
新規または現在値確認済み、明示設定要求との整合を確認する。
「作成」という文言だけで対象が実機に存在しないとは判断しない。

## 5. 中断・再開時の確認

1. 本書の第1節と未コミット変更を確認する。過去記録の「次回」より現在の着手点を優先する。
2. 実装とモデル評価を分け、仕様変更は基本・詳細設計、手順変更は実装ガイドへ反映する。
3. 既存カタログ・原本・派生物・索引を勝手に更新せず、必要なら候補一式で検証する。
4. demo21は旧入力・検索を保持しているため再開しない。
   demo22・23・24も過去評価として保持し、改善後は新しい出力先を使う。
5. `--resume`は警告付きで完了したgenerationを再利用する。補足や意味審査の再生成を期待して繰り返さない。
6. 外部API評価は呼び出し回数・入力条件・出力先を明確にし、モック結果と区別して記録する。
7. 再開時にはここを更新し、未実装案を実装済みに変えるのは実装と検証が終わってからにする。
